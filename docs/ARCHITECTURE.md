# Architecture

How Decimal is built, by subsystem. Each section opens with its status so a reader knows how much to trust it as a foundation.

Verified against the code on 2026-09-17; the exception agent section on 2026-09-24. When you change a subsystem, update its section in the same commit.

| Status | Meaning |
|---|---|
| **Live** | In daily use, actively developed. Build on it. |
| **Frozen** | Wired, tested and reachable, but not developed since mid-August 2026 and not proven in production. Do not extend without a product decision. |

## What the product does

Decimal is an accounts-payable product. A bill arrives by upload or forwarded email. A vision model reads it into structured fields. A person checks it and picks a category for each line, and an approval flow routes it to the right people. When it is approved it is posted to QuickBooks Online as a bill; the payment is recorded against it when it is paid.

The final step, paying the bill, is the frozen part. See [Payment execution](#payment-execution-frozen).

## Runtime (Live)

One Docker Postgres on port `54329` holds three databases that cannot see each other.

| Database | Used by | API | Frontend |
|---|---|---|---|
| `usdc_ops_local` | `make dev`, what a human looks at | `:3100` | `:5174` |
| `usdc_ops_bench` | `make bench`, what an agent drives | `:3200` | `:5274` |
| `usdc_ops_test` | `make test`, truncated on every run | | |

`api/src/index.ts` starts the HTTP server and then four background workers:

- `registerPaymentApprovalBridge()` connects approval outcomes to bill state.
- `startSettlementReconciler()` verifies on-chain settlement. Frozen subsystem.
- `startAccountingSync()` pushes and pulls QuickBooks data.
- `startInboundEmailIntake()` turns forwarded emails into draft bills.
- An approval timer sweep escalates overdue approval tasks. It never auto-denies.

**AI providers** (`infra/ai.ts`). Every AI feature runs on whichever provider has a key, Claude or OpenAI. With both set, `AI_PROVIDER` says which goes first; unset, Claude does. An account that turns work away (out of credit, a key refused) is passed over for ten minutes while the other has a key; a rate limit is not that. A single answer goes through `chat()`: the call site builds its request in OpenAI's chat shape as it always has, and on OpenAI it is sent exactly as built (through `infra/openai-params.ts`). On Claude it is translated: the system prompt apart, page images as image blocks, a strict schema as structured output without the numeric and length limits Claude's decoder refuses (each caller validates what comes back), a schema bigger than the decoder compiles (more than 16 fields that may be null, or 24 optional ones; extraction's has 35) asked for in the system prompt instead, with the nulls a reply leaves out put back, "JSON only" as text the JSON is taken out of, no temperature, and adaptive thinking at low effort unless asked. Claude answers single calls on `ANTHROPIC_MODEL` and runs the agent loop on `ANTHROPIC_AGENT_MODEL`, both `claude-haiku-5-5` unless set: the same list price as `gpt-6-luna`. On 2026-11-08 the setup eval passed 16, 17 and 15 of 18 on it in three runs, where Opus 5.5's two full runs passed 15 and 16, for about a fortieth of the cost. `infra/model-cost.ts` prices a call at list price. With no key, nothing calls a model and every feature works without one. On 2026-11-08 the 31 invoices of the catalog (`synthetic_data/invoices/`) went through extraction on Claude Haiku 5.5 on the bench, each in an organisation of its own: 28 read exactly as the catalog has them, the one in euros was refused for its currency, and both credit notes were flagged as credit notes.

## Request pipeline (Live)

`api/src/app.ts` mounts middleware and routers in a deliberate order.

1. Request logging, CORS, public rate limiting.
2. Raw body parsing for the inbound-email webhook only, so its signature can be verified. JSON parsing for everything else.
3. **Public routers:** health, capabilities, OpenAPI, auth, public invites, the QuickBooks OAuth callback, the inbound-email webhook.
4. `requireAuth()`. Auth is a session token (`auth/sessions.ts`) sent as a bearer token.
5. `capabilityAccessMiddleware()` enforces role-based access on organization-scoped routes. Owners and admins bypass it.
6. The server-sent events stream and the Solana RPC proxy. They mount before idempotency because one is long-lived and the other is a pass-through.
7. `idempotencyMiddleware()`.
8. **Authed routers:** user wallets, automation agents, organizations, invites, ops, treasury wallets, wallet authorizations, counterparty wallets, invoices, inbound email, bills, payment orders, proposals, approvals, accounting.

Conventions that hold everywhere:

- **Money is bigint minor units.** USDC raw is dollars × 10^6. Never floats, never cents.
- **JSON payloads are validated with Zod** at the boundary.
- **ESM throughout.** Relative imports use explicit `.js` extensions even in `.ts` source.

## Database (Live)

**The schema is SQL-first.** `postgres/init/*.sql` is the source of truth, applied in filename order by `scripts/db-setup.sh` on every `make dev`, `make bench` and `make test`. Every file must stay idempotent because it re-runs on every startup. There are no Prisma migrations. Prisma is a typed client only: after editing SQL, update `api/prisma/schema.prisma` to match and the Makefile regenerates the client.

**Two schemas.**

- `public` holds the product tables, mirrored in `schema.prisma` (37 models). The main groups:
  - Identity: `Organization`, `User`, `OrganizationMembership`, `OrganizationInvite`, `AuthSession`.
  - Bills: `PaymentOrder` is the bill. Also `InvoiceDocument`, `InvoiceDocumentPage`, `PaymentOrderEvent`.
  - Bill collaboration: `BillComment`, `BillQuestion`, `BillFieldChange`, `AiSuggestion`, `AiSuggestionOutcome`.
  - Vendors: `Counterparty`, `CounterpartyWallet`.
  - Accounting: `AccountingConnection`, `AccountingAccountMap`, `AccountingSync`, `PaymentOrderGlCoding`.
  - Inbound email: `InboundEmailMessage`, `InboundEmailAttachment`.
  - Payment execution, frozen: `TreasuryWallet`, `DecimalProposal`, `SpendingLimitPolicy`, `SpendingLimitExecution`, `TransferRequest`, `ExecutionRecord`, `AutomationAgent`, `AgentWallet`.
- `approval` holds the approval engine (21 tables, defined from `002-approval-engine.sql` onward). It is **deliberately outside Prisma** and is reached only through raw SQL in `api/src/approvals/store.ts`. Do not model these tables in Prisma.

In code and the database a bill is a `PaymentOrder`. In every piece of UI copy it is a "bill". Its states are `draft`, `submitted`, `proposed`, `executed`, `settled`, `cancelled` (`payments/order-state.ts`). The operator sees five buckets derived from those: Draft, In approval, To pay, Done, Needs attention.

## Bill intake and review (Live)

`api/src/payments/`, the largest module.

1. **Arrival.** Upload (`invoice-intake.ts`), CSV (`csv-intake.ts`), or forwarded email (`agents/inbound-email-intake.ts`). Only team members may forward mail in. An upload is stored first (`invoice_documents`, status `processing`) and read in the background: the bill is made once the reading and its categories are in, and the document turns `processed` after the bill's opening checks. A document that defeats the reader still becomes a bill, with every field marked unreadable (`unreadableRow`); the draft and the workbench row say `unreadable`, so the screen shows the file rather than the placeholder vendor and cent. A document that fails on our side (a provider down, no key) or gives no bill (no invoice in it, a currency other than US dollars) turns `failed` with a plain reason, and `GET /invoice-documents/:id/status` says whose fault it was (`failure`: `ours` or `no_bill`). A failed document can be read again (`POST …/retry`: that document, re-read from its stored bytes) or taken off the list (`POST …/remove`: status `removed`, the file stays stored, and uploading it again reads it again). Both need `bills.create`, as uploading does.
2. **Extraction.** `document-extract.ts` sends the document to the model on whichever provider has a key (see AI providers) and validates the result with Zod into an `ExtractedInvoice`. Scans and photos are rendered to images for a vision model. A PDF with its own text layer takes a cheaper text-only path. The models are config, not code: on OpenAI `openAiModel` and `openAiTextModel`, default `gpt-6-luna` (chosen 2026-09-30: same accuracy as gpt-4.1-mini on the 27-invoice catalog, a quarter of the price); on Claude `ANTHROPIC_MODEL` for both paths, checked against the catalog on 2026-11-08 (see AI providers). Measured that day on Claude Haiku 5.5, a text-layer invoice cost about $0.001 (about 5,800 tokens in, three quarters of them the fixed instructions, and 750 out) and a scan about $0.0013. Scans' word boxes come from tesseract, locally. Every Chat Completions call goes through `infra/openai-params.ts`, which translates a body for reasoning models: `max_completion_tokens` with headroom, `reasoning_effort` (`none` when the call has tools, since Chat Completions refuses tools with reasoning; `low` otherwise), and no `temperature` when reasoning is on.
3. **Provenance.** `doc-provenance.ts` locates every extracted value in the document's text layer and stores its page and bounding box. This powers "click a field, see where it came from" in the UI.
4. **Flags.** `bill-flags.ts` evaluates problems. Three are policy gates: `duplicate-check.ts`, `vendor-payable.ts` and the org bill ceiling. A vendor hold is put on and released on the vendor's page by an admin, always with a reason; `blocked` is the primary admin's alone and the app shows it but never offers it. The hold's flag says so, and its Review the vendor opens that vendor's page. `vendor-similarity.ts` catches near-duplicate vendor names. Each flag carries its own resolutions, and a resolution names who may take it: `anyone`, `admin`, or `primary_admin`.

   Duplicates are settled **per pair**, not per bill. A duplicate flag sits on both bills, and "not a duplicate" answers for the pair: the clearance names the bills it settles (`against`), and a pair cleared on either bill is settled on both. A bill uploaded later is never covered, because nobody has looked at that pair. Every duplicate check — the draft flag, the workbench, confirm, release, the autopay veto and the exception agent — asks `settleDuplicates` / `settleDuplicatesWith` in `duplicate-check.ts`, so they cannot disagree.

   The bill ceiling is checked in three places and they must not drift: the draft flag, the confirm gate in `bills.ts`, and `release-gate.ts`. A bill may be let past it one at a time — `ceiling-exception.ts`, primary admin only, with a reason, leaving the ceiling itself unchanged. All three gates ask `activeCeilingException`, which returns a grant only while the bill is still for the amount it was granted for. Changing the total voids it.
5. **Review.** `bills.ts` serves the workbench list and the draft screen. Each workbench row says who an approval waits on (`waitingOn`: everyone open at the first open step, so "Tom or Ines"), how far QuickBooks got (`posting`, from `accounting_syncs`), whether a draft was sent back, why a closed bill was closed, and the vendor record it belongs to (`counterpartyId`) with the email and address its document gives (`vendorContactOf`: what a person verified over what was read). A vendor keeps no contact of its own, so the Vendors pages show its newest bill's. Questions and comments live in the bill thread (`question-fields.ts`, `question-settle.ts`). The thread is a group chat (2026-10-21): a question names a person and holds nothing, and nobody clicks Answer. Whatever someone says on a bill with an open question goes to `POST /bills/:id/messages` (`postBillMessage`), and the answer judge (`answer-judge.ts`: Luna, or with no model the rule that whatever the person asked says is their answer) reads it against each open question. A message answers it (anyone who works on bills, not a Viewer and not the asker), says the person asked can't (only them; it goes back to the asker), withdraws it (only the asker), or does nothing to it. A message that settles a question, or comes from the person asked, lands in the thread as a comment and the question keeps it (`answer_via = 'message'`, `answer_comment_id`); anything else comes back `posted: false` and the screen puts it to the companion. A deed that does what a question asked settles it too (`answer_via = 'deed'`). The answer and close routes (`/questions/:qid/answer`, `/close`, `answer_via = 'words'`) remain for the old pages until they are removed. Taking part is wider than editing: in every state, anyone who works on bills may answer, reply and comment (`canJoinConversation`), approvers included, so the one deciding a bill can ask before they do; Viewers read it without joining in. Questions asked before 2026-10-14 may still hold an approval step in `request_info`; answering or closing one releases it. Every edit is logged (`bill-history.ts`).
6. **Confirm.** The reviewer confirms, which submits the bill to the approval engine. Verification always happens before routing.

Frontend: `pages/Bills.tsx` (list) and `pages/bill/` (the redesigned bill page). A bill in review opens there: the Decimal agent box with its findings, the ways to settle each and the reply line, then the fields, line items, History and the document pane, saved as you go. The page writes every decision as its taker's own message, so the draft says what it needs for that: each work-log override names the `rule` it set aside, and `tradingNamesFromHere` lists the names recorded as the organisation's own off this bill. A question is its asker's message, "@name" and the words (`AgentBox.tsx`): the person asked sees it on a maroon band ("Question for you") with "Answer {name}…" in the reply line, everyone else sees a row for whoever it still waits on at the end of the thread (their face with a yellow badge, "Hasn't answered yet"), and once settled it says in one grey line who answered it. Sending without an @name goes through `/messages` first whenever a question is open, so the message shows faded while Decimal judges it. The companion's ask cards (drafted, already asked, can't be asked) are `pages/bill/AskCard.tsx`.

A file being read opens on `pages/bill/Reading.tsx` (5r): every box breathing, the file beside it as its pages are made. Once its bill exists, the bill's own page takes over (fetched first, so nothing blank comes between) and the reading lands part by part, one 220 ms tick apart: the vendor, the invoice, its figures, the lines, their categories (`landsAt`, `lineLandsAt` in `model.ts`). Until the document is `processed` the page says Extracting and nothing can be changed or sent. A file no bill came out of shows Decimal's reason, with Read it again and Remove this file. A bill nothing could be read from (5u) shows every box as Not read and the file faded, with Not a bill? Remove this file (closes it as unreadable, admins only) and Enter the details by hand; typing anything turns it into an ordinary review, and its placeholders never show.

A bill past review opens on `pages/bill/Record.tsx` (5d to 5h), its facts read-only (`Facts.tsx`: who settled a value shows on hover, a changed value keeps the printed one struck through beside it). At the top of the left column is its route (`Chain.tsx`): who brought it in, who sent it, then each approval step as beads, solid as far as it got and dotted beyond, the latest round only. An either-one step draws whoever approved on top and the one not needed pale, so the detail keeps a satisfied step's alternatives as `skipped` steps. On the right, Decimal's box (no findings; the reply line stays open) and History, open. The bar holds what the viewer may do now. On their own step: Ask a question (to the sender; nothing waits on it), Send back (an approval `reject`, with a reason) and Approve, greyed with the reason when `viewer.cannotApprove` (when the sender is alone on the step, the reason says what unblocks it: No self-approval turned off on Organisation). While it waits on others, the sender may ask to take it back (`/recall-request`: the approval holds until an admin gives it back or keeps it, and an admin's own ask is granted at once) and withdraw the ask. Approve and Send back are hidden while a take-back is asked, because the engine doesn't check the hold. An admin may send an approved bill QuickBooks hasn't taken back to review (`/send-back`). A failed post shows QuickBooks's reason, whether the sweep will still try again (`posting.retrying`), and Try again for whoever edits bills. A closed bill says who closed it and why, linking the bill it duplicates (the duplicate flag's answers carry its `targetId`). A bill sent back is a draft again, so it opens in review with the route it came back by and the reason in a beige box above Decimal's (5e). View the document opens the file in a sheet in every state past review.

## Exception agent (Live)

`api/src/exceptions/`. When a flag fires, an agent investigates it before anyone opens the bill and recommends one of the flag's own resolutions, with evidence. It never acts: the flag still blocks, and a person confirms. Only `possible_duplicate` has an investigator so far.

- `agent.ts` is a generic tool-calling loop (6 turns, one timeout, a terminal tool ends the run), and the integration setup and the companion chat run on it too. `setExceptionAgentRuntimeForTests` replaces the model with a script. With `ANTHROPIC_API_KEY` set the loop runs on Claude (`ANTHROPIC_AGENT_MODEL`, default `claude-haiku-5-5`, medium effort); without it, on `OPENAI_AGENT_MODEL`, falling back to `OPENAI_MODEL`. The provider is chosen as for every AI call (see AI providers), and a run keeps the model it started on, so a conversation never changes provider halfway. On Claude the server-side fallback for a policy decline is asked for only on Opus and Sonnet models; Haiku has none. With no key, nothing runs and flags behave as they always did.
- `claude.ts` turns the loop's chat shape into a Messages API request and back, through the official SDK. A reply goes back exactly as Claude sent it, because its thinking is signed and a rebuilt copy is refused. A list of types in a tool schema becomes `anyOf`, which is the only way strict mode takes it. A conversation that starts with a reply gets a first turn from the person. A policy decline re-runs server-side on Anthropic's fallback (`fallbacks: "default"`), and each call reads the run so far from cache. `make test` and `make test-one` blank both keys, because Prisma loads `api/.env` into the test process.
- `duplicate-logic.ts` is everything that must not be a model: bill facts in the draft screen's precedence, a line-by-line comparison, the pair key and fingerprint, the verdict → action mapping, and the validator. Findings must cite refs a tool returned in that run, and figures that contradict a verdict cap its confidence. Text the model writes is cut to fit but never mid-word: the reason (which a person records) after its last whole sentence, anything else at a word with an ellipsis. Upload times reach the model already written for people (`uploadedForPeople`), because it copies what it is shown.
- `duplicate.ts` is the investigator: tools `get_bill`, `compare_bills`, `vendor_history`, `read_document`, and a strict-schema `submit_finding`. Verdicts are `duplicate`, `replacement`, `not_duplicate` and `unsure`. A duplicate keeps the older bill; a replacement keeps the newer one. Exactly one side is ever closed: that side is advised `not_ours`, and the side to keep is advised `close_other`, never to clear. A clearance settles the pair from either side, so clearing the bill to keep would let the copy through; closing the copy is enough, because a closed bill stops matching.
- `briefs.ts` decides when it runs and stores the answer in `bill_exception_briefs`, **one row per bill pair**, since a duplicate flag sits on both bills. It runs from exactly two places: after intake, and when `getBillDraft` is read. Never from `flagsForOrder` or the workbench. A read claims the run with one atomic upsert, so concurrent reads start one investigation. A fingerprint over both bills (including whether each was cleared) re-runs a stale brief.
- Every recommendation goes to the suggestion log under stage `exception_brief`, and clearing, closing or asking logs what the person did against it (`recordBriefOutcome`). That is the agreement rate.

Frontend: the brief renders on its flag in the bill page's agent box (`pages/bill/Findings.tsx`). The recommended way to settle it is the filled pill, and every pill opens a card in the conversation whose button acts, so nothing happens until a person confirms. A duplicate shows the two bills side by side, fact by fact (`brief.comparison`: "This upload" against "The original" or "The later copy", each figure marked as matching or differing), with a link that opens the other bill. Clearing the flag asks for a reason, and when the brief calls the bill a copy or a replacement it warns that both bills can then be approved and posted. Evaluate with `api/scripts/exception-eval.mts` on the bench. It runs the real pair B4 against A2 and the X-series (section X of `TESTING-INVOICES.md`). It uploads each file under a neutral name: the investigator reads a document's name, and the catalog's names state the answer. On 2026-11-12, on Haiku 5.5, three runs got all 21 verdicts right, none of them confidently wrong. X6, a pair nothing tells apart, came back unsure at low confidence each time.

Flags about ONE bill get a finding instead (`exceptions/findings.ts`), worked out on every draft read and attached as `flag.finding` { headline, points, recommended { action, reason } }. The screen shows it in the flag's box (inside the companion note) with the recommended resolution as the primary button and its reason prefilled; a person still clicks.
- **looks_like_statement**: the statement's own rows joined to our bills (`document-reconcile.ts`): what is open and not in Decimal (chase it), what the vendor marks paid that we never saw. Without rows, its listed invoice numbers looked up instead.
- **looks_like_credit_note**: the bill it credits — one of the vendor's real invoice numbers found in its text — or the vendor's open bills big enough to take it.
- **lines_do_not_sum / total_does_not_reconcile**: arithmetic: a line whose quantity × price disagrees (misread), a gap equal to one line (missed or read twice) or to the tax, or the document disagreeing with itself (ask the vendor).
- **addressed_elsewhere**: one model call — is the bill-to name us? — made in the background on first read and remembered on the bill (`metadata.addressedCheck`) for that name; same → This is us, different → Not ours, unsure → Ask. `setAddressedCheckForTests` replaces it in tests. Answering This is us adds the bill-to name to the organisation's other names (`organizations.trading_names`, each entry saying who added it and off which bill). Admins see them on Organisation and can take one off (`payments/trading-names.ts`): the entry is marked removed, with who removed it, rather than deleted, so bills addressed to it are asked about again, the bill it came from keeps it in its history, and Undo puts the same entry back.

## Companion (Live)

`api/src/companion/`. The companion does the work before a person looks and shows it happening. The landing page is its console.

- **Steps** (`steps.ts`, table `companion_steps`). A job is one document. Intake writes each stage as a step as it happens (received, opened, read, figures checked, categories, vendor, checks) with a sentence the server writes once. The duplicate investigation writes a step for itself and one per tool call, by wrapping each tool's `run`. Recording is best-effort and never throws. Steps left running by a crash are closed as interrupted when the console loads.
- **Readiness** (`readiness.ts`). A strict verdict per draft: ready only when nothing calls for judgement, otherwise the single most important reason. Attached to each workbench row as `companion`.
- **Console** (`today.ts`, `GET /companion/console`). Running: documents being read and bills being investigated. Waiting on you: approvals, drafts needing input, bills sent back, unreadable documents, ready drafts to sign off. Done: bills that moved past review in the window. The window is "since you last looked" (`companion_views`; a gap over 30 minutes starts a new visit). A bill waiting on you is never also done, and a draft still being worked on is running, not waiting. Each person sees their own work; admins also see who is holding approvals.
- **Jobs** (`GET /companion/jobs/:jobId`). A job's steps and bills, to whoever may see its bills (`involvedBillIds`).

- **Chat** (`chat.ts`, `chat-tools.ts`, tables `companion_chats` and `companion_messages`). Ramp Stack style: a person asks, the answer is worked out in the background with the exception agent's loop (`runAgent`, with the conversation as history), and each tool call appends a thought to the answer while it runs. Tools are read-only and read through the same functions the screens use, so the companion sees exactly what the asker can. Bills (`chat-tools.ts`): `find_bills` (by invoice number, vendor, state, date received, amount, and due date: `dueFrom`/`dueTo` compare the day each bill is due, kept as midnight UTC, and a search by due date leaves out bills already paid or closed), `get_bill` (with QuickBooks sync status), `spend_summary`, `vendor_profile` (with any payment hold), `whats_waiting` (with questions asked of you). The organisation (`chat-tools-org.ts`): `team` (members, access, roles, and a code-defined list of which job is whose), `approval_trail`, `bill_history` (changes, comments, questions, lifecycle), `approval_rules` (the published flow in words, the ceiling, separation of duties), `categories`, `what_i_know` (the lines learned, per vendor). The prompt carries the team's time zone so UTC timestamps are converted. The answer is a few plain sentences (lines starting "- " where a list is the point), the bills it rests on, action cards, and up to three questions worth asking next (`followUps`, offered as chips under the latest answer); bill ids a tool never returned are dropped. Tables were dropped on 2026-10-21, so only older answers carry any. The prompt knows where it is answering: on Home each bill in `billIds` shows as a card under the message, so the message is the answer itself and never lists the bills again. Chats belong to the asker.
- **Inbox** (`inbox.ts`, table `inbox_seen`; `GET /inbox`, `POST /inbox/seen`, `/inbox/seen-all`, `/inbox/replies/:questionId/done`). One item per bill per person, with every line that wants something of them. Every line is derived from state every time and never stored, and says who it comes from (`who`, a face; none for what Decimal raises itself), what they did (`lead`: "Zara Okafor sent it for your approval", "Marcus Bell approved it; your step is next", "Leah Morgan asked") and their own words apart (`quote`: the question, the answer, the reason it was sent back). The lines: your approval, a question asked of you, a reply to a question you asked (answered, or couldn’t answer), a bill sent back with who sent it and why (`metadata.sentBack`), a draft to review or sign off, a bill QuickBooks refused (admins), an unreadable bill, and a file no bill came out of ("Something went wrong while reading it" when the fault was ours, never the raw error). A line is new when it is later than the person's last look at that bill; the bill page marks the bill seen when it opens (`POST /inbox/seen`), so opening a bill is reading what the Inbox had on it. A file has no page, so it is never new. A reply stays until the asker opens the bill after it, acts on the bill, or the bill closes (the legacy chat page's workspace can still tick it done). `count` is the number of lines, and is the sidebar's badge. Every ask from one person to another is a question on the bill: nudges (`inbox_asks`) were removed on 2026-10-14, because once a question stopped holding the bill the two no longer worked differently. `pages/Inbox.tsx` (22b) is one table with a row per line: approvals first, then questions and replies, then the team's pile (sent back, QuickBooks, review, can't read, sign off), earliest due first within each. The tabs All, New, Approvals, Questions and To review count lines and open from `?tab=`; the search matches every column and the line; ↑ and ↓ move the cursor and Enter opens it. A row only opens its bill: no Done, no quick actions, no agent, no times.
- **Learning, per vendor + line, in the background** (`accounting/line-memory.ts`; `knowledge.ts`, `GET /knowledge`, `POST /knowledge/lines/forget` with `{ counterpartyId, description }`; `forgotten_lines`). A category belongs to a VENDOR + LINE (Zaid, 2026-10-19): per line because a vendor sells different things (2026-10-01), per vendor because the same words are different purchases from different vendors (an "Annual license" from a software company is a subscription, from the city a permit). Every line on a confirmed bill, and every line whose category a person changed on a saved draft (against `proposedLineCategories`), is a precedent for that bill's vendor. A new draft line takes the category of the closest precedent from the same vendor when they read as the same thing (Jaccard ≥ 0.6 over the description's words, with quantities, dates, months and plurals dropped; newest wins a tie), and records `categoryFrom: memory` so the bill note can say which bill it is like. Another vendor's line never fills a line as known. Lines that are similar but not worded the same, and lines only another vendor has settled, go to the model: at upload, `suggestOcrCodings` shows it up to 25 of the team's settled lines (`relevantPrecedents`: one per kind of line, word-sharing ones first, then the newest), told to follow them only for the SAME PURCHASE (the same kind of thing, bought the same way: a subscription is not a licence, a service is not the product it is about, a rental is not a purchase; a different use, project or size does not change it), and to quote the line it followed (`like`, accepted only if it was shown), which becomes `categoryFrom: similar` (naming the vendor when the line was another vendor's). That is still a guess. `api/scripts/line-precedent-eval.mts` measures this against the real model: 13/13 on three runs (2026-10-02), including subscription traps and held-out lines the prompt does not mention. Only matches from the same vendor count toward readiness. Order per line: line memory, the model's reading of the line, a label the document prints on it, the bill-level guess. Nothing is taught explicitly and nothing is announced. There are no vendor defaults (removed 2026-10-19, with their tables `vendor_coding_rules` and `forgotten_habits`): a category for a whole vendor said nothing true about any one line, and it marked a vendor's drafts as known when every line was a guess. Readiness counts a draft's categories as known when every line matches a precedent from another bill of the same vendor, or was settled on this bill. "What I know" lists each vendor's kinds of line with the bill and person that last settled them; whoever codes bills (`bills.edit`) can forget one for that vendor, after which only that vendor's lines settled since can teach it again. Forgets made before 2026-10-19 named no vendor; `033-forgotten-lines.sql` moved each onto the vendors whose bills carry that exact line. The intake job's categories step says which lines are known from the vendor's earlier bills and which are suggestions. A finished setup teaches too (`accounting/books-lines.ts`): what repeated in the company's books, and what the person decided in setup, apply to the vendor here with that cleaned name or linked to it, so a vendor's first bill is known, and the screen says it came from their books. A person's later decision outranks it by being newer, forgetting works the same way, a line the person said to pick each time is filled in by nothing, not even a later bill, and disconnecting stops all of it, as the copy goes.
- **Asking people** (`ask_person` card, `ask-classifier.ts`). The companion names a teammate and the ask; code resolves the person (ambiguous names match no one), reads their inbox item without tidying it, and Luna decides whether they already have it (an info card, nothing to send: the card says so, and the answer's text no longer repeats it) or not (a question through the existing Ask, which holds nothing). Someone who only views bills cannot be asked: the card says so and sends nothing (`cannot_ask`), and the prompt tells the model not to try. A plain rule decides when there is no model.
- **Action cards** (`actions.ts`). The companion proposes, a person clicks: send a ready bill for approval, close the copy in a duplicate pair, clear a duplicate flag, approve a bill waiting on you. The model names only a kind, a bill and a reason; code decides whether it fits the bill as it is now and builds the exact request. The button calls the bill's own endpoint as the person clicking, so every permission check and gate runs at the click (separation of duties included). `POST /bills/:id/confirm-as-read` sends a ready bill exactly as read. Outcomes are recorded on the card; dropped proposals are logged as `companion_action.dropped`.

Frontend: Home (`pages/Home.tsx`, `home.css`; design 4a) is the chat's home. On the left, Waiting on you sums the Inbox (lines by tab, how many are overdue and new, Open Inbox), and Needs attention shows up to six bills from it that are overdue or due by Sunday, one card per bill in the colour of its most pressing line. On the right, Decimal's box: a greeting with one sentence about what is waiting, a pill while files are being read, and three suggested questions that fill the field (they never send). Asking turns the box into the conversation in place: the asker's message, then the answer with its live thoughts, a card per bill it rests on (vendor, number, amount, due date, and a chip in Bills' words from `pages/billStatus.ts`) that opens the bill, any ask cards, and follow-up chips. The box grows to full screen (one element moving, the page blurred under a scrim; Esc, the scrim or the icon return it) and Start over, only there, clears it. The chat id is kept per tab in `sessionStorage`, so opening a bill and coming back finds the conversation. Nothing on Home acts on a bill. The legacy `/chat/:chatId` page (`pages/Chat.tsx` in `pages/CompanionRail.tsx`'s frame) remains until the old pages are removed.

- **On the bill's own page** (`bill-note.ts`, `GET /bills/:id/companion`; `companion_chats.bill_id`). The companion's reading of one bill: whether it is ready and why not, where it stands, what the viewer's Inbox wants of them on it, the document's steps, and the viewer's latest chat about it. It only gathers what exists elsewhere and is read-only. The redesigned bill page uses two parts of it: the agent box reopens that chat, and History folds the steps under Decimal's reading. The note that showed all of it under the bill's heading, and its `companionOnBill` switch, went with the old bill page. A bill chat is an ordinary chat with `bill_id` set: the model is told which bill "this" is on every turn (the person's words are stored as written). `get_bill` carries the duplicate investigation's finding (`peekDuplicateBrief`, read-only, current pairs only) so the chat repeats it instead of re-deriving it and disagreeing.
- **Quick pass through ready bills, API only** (`ready-pass.ts`, `GET /companion/ready`, `POST /bills/:id/confirm-as-read`). The drafts the companion rates ready (strict: see `readiness.ts`), soonest due first, for someone with `bills.edit`. `confirm-as-read` sends one exactly as read and re-checks readiness at the click, so a bill that changed since the list was made is refused rather than sent. Its screen (Send, Skip and Stop, one bill at a time) went with the old bill page and the redesign has none, so no screen calls these two routes. A ready bill shows as "Checked" in Bills.

**Action cards (`actions.ts`): go there, or do it here** (Zaid, 2026-10-02: a person judges a bill with the whole bill in view, not from a narrowed card). A card about a bill — `look_at` (with a `focus`: a field, a line, the totals or a flag), `approve`, `send_for_approval`, `close_duplicate`, `clear_duplicate` — never acts: it carries `open { path, focus }` and opens the bill's own page; the bill page lands on `[data-focus=…]` (scrolls, outlines it, highlights the same spot on the document) and the note shows "From your chat: <reason>" (handed over in `sessionStorage`). The fit is checked exactly as before (only someone who could do it, only when the bill allows it). The card that acts is the one that is not a judgement about a bill: asking a colleague a question. Its request is built in code and sent as the person who clicks.

## Approval engine (Live)

`api/src/approvals/`. An in-house routing and approval system with three configurable stages: review, approve, release.

| Layer | File | Job |
|---|---|---|
| L1 | `l1.ts` | Resolves people, seats and hierarchy. |
| L2 | `compile.ts` | Turns a policy set plus an approvable into a pinned plan with provenance. |
| L3 | `sod.ts` | Separation-of-duties veto pass. Org-configurable, never hardcoded. |

Around the layers:

- `flow.ts` translates between the rules Approval rules edits and engine policy. Admins publish them as well as the primary admin (`governance.edit`). `flowProblems` refuses rules that would hold or misroute a bill: a step with nobody on it, an amount split at $0, a vendor or category split with nothing picked, a path with no step, or someone no longer on the team. Every published step escalates after 72 hours (`slaHours`), as the built-in route's does. The organisation keeps one draft (`approval.flow_drafts`), saved as an admin edits; it may hold a split nobody has filled in, and only people who can edit the rules see it. `testFlow` (`POST /approvals/flow/test`, Test a bill) walks the rules on the canvas for a made-up bill and applies what compiling would: who holds the Approver role, whether the sender may approve (Organisation's separation settings), the refill of a step left with nobody (approvers, then admins, then the primary admin) and a lowered quorum. A walk stops at a split that isn't set. Before any rules are published it shows the built-in route. A category split compares the names a bill line is coded to (`categoryNamesFor`: the QuickBooks chart when connected, the built-in one otherwise).
- `roles.ts` and `permissions.ts` hold the prebuilt role bundles and the `all` versus `involved` record scope.
- `lifecycle.ts` runs tasks and sweeps overdue ones. It escalates and never auto-denies.
- `recall.ts` and `out-of-office.ts` handle pulling a bill back and substitute approvers.
- `protections.ts` holds the organisation's policies and their record. Turning one off or back on, and changing the bill ceiling, take the primary admin's password when the account has one (`auth/confirm-password.ts`; a wrong one is a 403 `wrong_password`) and append a governance event (`protection_relaxed`, `protection_retightened`, `ceiling_changed`) that `latestPolicyChanges` reads back as who changed it last. Turning No self-approval back on also clears the old Approval flow switch (`org_settings.submitter_can_approve`), which let senders approve with nothing on the record; Organisation reads that switch as No self-approval off for everyone. Nothing can set it, or the other two old switches (`clerk_can_approve`, `approver_can_release`), any more: `POST /approvals/separation` went with the old page, so an organisation keeps whatever it had and only the GET remains.
- `policy-exceptions.ts` lists the bills approved with a policy set aside, for Organisation's Exceptions: approved by whoever sent them, or allowed over the ceiling. The last 90 days, 100 at most.
- `store.ts` is the only file that touches the `approval` schema.
- `wiring.ts` and `hooks.ts` connect the engine to bills.

`payments/approval-bridge.ts` is the glue. An approved bill is marked submitted and a release run is spawned. A rejected bill goes **back to review** with the reason. Rejection is never terminal.

Frontend: Approval rules (`pages/ApprovalRules.tsx` with `pages/rules/`, `rules.css`; design 1a–1c) draws the rules as a tree on a canvas that pans and zooms. An admin edits a step or a split in an editor beside it, adds one from a "+", undoes with ⌘Z, and publishes; everyone else sees the published rules without the tools and a line naming the admins. Test a bill, open to all, draws the route a made-up bill takes in maroon and lists who approves it. The design's Decimal agent is left out (`docs/OPEN-WORK.md`). Also `pages/Approvals.tsx`, `pages/Protections.tsx` (shown as Organisation) and `pages/Team.tsx`.

## GL coding, QuickBooks and Xero (Live)

`api/src/accounting/`.

- Each draft line's category, in order: line memory (`line-memory.ts`: what the team settled for this vendor's lines like it), the model's reading of the line, a label on the document, the bill-level guess. Corrections teach line memory. There are no vendor defaults (removed 2026-10-19).
- `ocr-coding.ts` and `default-chart.ts` supply the chart of accounts, from the team's books (`chartSystem`: the system bills post to, else QuickBooks or Xero, whichever is signed in), with a built-in fallback when neither is. From Xero it leaves out bank accounts, system accounts (accounts payable, tax, retained earnings and the like) and archived ones, none of which a bill line can use, and names account types in Xero's words.
- `quickbooks.ts` and `connections.ts` handle QuickBooks Online OAuth (`setQuickBooksForTests` swaps in a fake client). Each request builds its own client from the stored tokens. Renewing a run-out access token is shared by every request in the process, and a refused refresh token that another process already spent (the stored one is newer) is not taken for a lost sign-in.
- **Categories are chosen in review.** At confirm, `recordReviewCoding` turns each line's category name into a coding row (`payment_order_gl_codings`) with the account id from the books' chart, or the standard list when not connected. The picker offers the whole chart except what a bill line can't use: Accounts Payable and Accounts Receivable in QuickBooks, and in Xero the accounts above.
- **Connecting only reads; a person turns posting on.** Signing in saves the tokens and writes nothing to the customer's books, not even an account. The only way to turn posting on is the setup's Go (`POST .../integrations/setups/:setupId/go`, admins, no agent tool reaches it; see Integration setup below). It records who said yes and when (`accounting_connections.posting_enabled_at`), and every write below checks it. A bill approved before that moment does not post by itself (`billsApprovedSince` in `approvals/store.ts`). Signing in again to the same company keeps the yes; a different company loses it and its account map, and so does disconnecting. A team posts to one set of books. `postingTarget` (`connections.ts`) is where approved bills go: the connection with a yes that isn't disconnected, the latest yes if there are two. Go is refused while another system's yes holds (`one_set_of_books` in `setup/gates.ts`), and a bill posted to one system never posts to another, so a team that moves keeps what it posted where it posted it.
- **Posting happens in two moments** (`account-sync.ts`, `sync.ts`). When a bill's approval completes, the approval bridge calls `syncApprovedBill`, which posts it to the posting target: a QuickBooks Bill, one line per category (`postBillToQuickBooks`), or a Xero bill (below). `books-poster.ts` is what posting needs from a system (`Books`): `quickBooksBooks` wraps QuickBooks' posting so nothing it sends or says changed, and `xeroBooks` is Xero's. Then the invoice file goes on that Bill as an attachment (`attachInvoice`, `QuickBooks.uploadAttachment`, one multipart request to `/upload`). It is best effort, because the bill is already in the books: a file QuickBooks refuses leaves the bill posted, with the reason in the sync row's `metadataJson.attachmentFailed`, and the id lands in `attachmentId` otherwise. It is done once, only on bills Decimal posted (not ones linked to an entry made by hand), and never for WebP, which QuickBooks doesn't take. Verified on a sandbox on 2026-11-08: the file read back from QuickBooks byte for byte. When it is paid (settled), `syncSettledPaymentOrder` records a BillPayment from the clearing account against that Bill (`recordBillPaymentInQuickBooks`); a bill paid before it was ever posted gets both at once. That payment half is frozen, QuickBooks only, and its clearing account now has to be mapped by hand. One `accounting_syncs` row carries both ids. Idempotent through QuickBooks requestids: on a real sandbox the same requestid returned the same bill, even with a changed body, and after a refusal it was a fresh try, so a retry works.
- **A bill posts at what was approved.** `linesToPost` (`sync.ts`) makes the lines come to the approved total: tax on its own line in the category of the largest line, cents lost to rounding on the largest line, and any other gap refused in words rather than guessed at, before anything is written. After posting it reads the bill back and compares totals. If QuickBooks recorded another total, the bill stays on the record with an error and never posts twice, and a retry looks again. It also sends the bill date and the due date.
- **Which vendor** (`vendor-match.ts`, `vendorInBooks` in `sync.ts`). A link the person made in setup, else the same name in the study's copy once case, punctuation and legal form are gone, else QuickBooks' own match by name (it ignores case), else it creates the vendor the bill names. Two live vendors it can't tell apart are refused rather than guessed. QuickBooks renames a vendor it makes inactive "Name (deleted)", or "Name (deleted-1)" and on, so the name looks free: an inactive one is found under that name too, and refused with the name it shows under, never made a second time. One name belongs to one record across customers, employees and vendors, so a business that is also a customer, or someone on the payroll, gets its vendor record as "Name (vendor)", made once and found after.
- **Already in the books** (`books-check.ts`). QuickBooks doesn't stop a bill entered twice: on a real sandbox it took a second bill with the same number from the same vendor without a word. Xero isn't trusted to refuse one either, and the same look runs there through Xero's reader. So Decimal looks in the books, live through the reader (`billsLike`), for one keyed in by hand: the same number from the same vendor, or, with no number on one side, the same vendor, amount and currency within a week. With the vendor's record known (setup's links, the study's copy, or where its bills posted before), its recent bills are read and a number matches however it is written (`sameNumber`). Known only by name, the number is asked for as written and as likely keyed (`numberVariants`), because QuickBooks matches a number exactly but for case: "INV 1042" finds "inv-1042" but "1042" alone doesn't find "INV-1042" (checked on a sandbox). Two numbers that differ are two bills, and bills Decimal posted itself don't count. It looks twice. Once in the background when a bill is opened (`ensureBooksCheck`, from `getBillDraft` only, never the workbench), under a lease and a fingerprint of what was looked for, in `bill_books_checks`, so the bill shows "Already in QuickBooks?" (or Xero), a warning that blocks nothing. And again just before it posts (`checkBeforePosting`), because approval can take days. That look may find the vendor by name in the books when nothing else knew it, so a held sync keeps that vendor (`externalVendorId`) and the look made when the bill is opened looks for it too. Without it, that look took the bill for a changed one, emptied what was found while it looked again with less, and a bill matched through that vendor alone (the same amount and date) held its posting with nothing on its page to answer (found on Xero's Demo Company on 2026-11-12). Anyone who checks bills answers on the bill (`POST .../bills/:id/in-books`): "Same bill" links the Decimal bill to that one rather than posting it (`linkedFromBooks` on the sync, its total checked as a posted bill's is), and "Different bill" lets it post. Unanswered at posting, the sync is `held`: nothing goes, the sweep leaves it, a retry only looks again, and it waits in the Inbox of whoever reviews bills until someone answers, when it posts or links at once. A "same" about a bill no longer there counts for nothing, and a linked bill someone later deletes in QuickBooks is unlinked, so the next try looks again. A read that fails fails the posting: it never posts blind. QuickBooks is never a step in the approval chain.
- **A bill in another currency doesn't post.** Decimal posts in USD only, so it fails with that reason rather than sending foreign figures as dollars.
- **A closed period.** A bill dated on or before the closing date doesn't post. The books' own date wins when they keep one, because it moves as they close each month (QuickBooks' close date; in Xero the later of the period and end-of-year lock dates); otherwise the date the person gave in setup (`integrations/setup/outcome.ts`).
- **A refusal reads plainly** (`plainQboReason` in `quickbooks.ts`), and a `Fault` on a 200 counts as one. Xero's (`plainXeroReason` in `xero-books.ts`) says each of its validation messages.
- **Xero** (`xero-books.ts`, through `httpXeroClient`). A bill is an invoice of type ACCPAY, entered awaiting payment (`AUTHORISED`), never a draft, with `LineAmountTypes` NoTax and `CurrencyCode` USD said every time. The supplier's number goes in `InvoiceNumber`, which Xero's screen calls Reference on a bill, with the bill date and due date. Each line is quantity 1 at its amount, its account by code (by id for an account without one), checked against the live chart first, so a Category archived since review is refused in words and nothing is written. The contact is the setup's link, else the same name in the study's copy, else Xero's own search for that exact name in any case, archived ones included, else a new one. An archived contact is refused with its name, never made a second time, since Xero keeps the name. After posting it reads the bill back by id and compares totals, as with QuickBooks, and a bill deleted or voided there since is gone (a linked one is unlinked). The invoice file goes on as one request of its bytes. Every write carries an `Idempotency-Key`. Before the bill is sent its key is kept on the sync row (`metadataJson.sending`). When no answer comes (a timeout, the network, a 5xx) it may have landed, so the next try within ten minutes sends again with the same key, which brings back the bill that landed, and skips the look in the books, which would find that bill and hold it as someone else's. When Xero refused, nothing was made, and the next send gets a key of its own. A bill that went in but couldn't be read back is recorded as posted (`PostedUnchecked`), and a retry reads it. Xero's documentation doesn't say how long it honours a key, so a send is replayed only within ten minutes of it; after that the look in the books catches a bill that landed. On the Demo Company a key sent again a minute later, and again nine and a half minutes later, brought back the same bill and contact each time, and Xero kept one. Whether Xero replays a refusal doesn't matter, because after one the next send has a key of its own. Only a real sign-in posts: the bench's made-up organisation has no Xero behind it, so a bill approved there fails saying so. Run on Xero's Demo Company on 2026-11-12 (`scripts/xero-post-check.mts`, from a seeded bench team that went through the setup and Go). A bill from a vendor new to Xero, with two Categories and 42.12 tax, made the contact and went in awaiting payment at 568.62, the tax on the larger line's account. Its PDF read back from Xero at the size uploaded. A bill from a supplier the Demo Company already had went to that contact, not a second one. Each showed as synced to Xero on the bill page and in History, and under Posted on the screen after Go. The checks before posting ran there the same day (the script's `replay`, `inbooks`, `locked` and `archived`). A bill Decimal's poster sent to Xero with no Decimal bill recording it, as a lost answer leaves one, held the Decimal bill uploaded for it, and "Same bill" from that bill's page linked the two. A bill dated before the lock date (30 September 2008) and a bill for an archived contact were refused in words, and nothing reached Xero.
- A category missing from the chart re-checks the live chart before failing, then fails with the category named. Failures retry in the background (`sweepUnsyncedSettledOrders`, up to five attempts; it also posts bills approved since posting was turned on that never made it, e.g. while the connection had lapsed) and land in the Inbox of admins and anyone with `accounting.manage`. A held bill doesn't retry by itself: it waits for an answer (above). A person retries from the bill's page or the Accounting page (`syncBillNow`, which resets the attempts first). An organisation without books to post to leaves no trace.
- The Coding inbox (coding bills after they were paid) was removed on 2026-09-30: categories are chosen in review, and bills post at approval.

The UI never says "GL coding". It says "Line items" and "Category".

Frontend: `pages/Accounting.tsx` (connection, account map, sync health, failures with Retry, and the posted-to-QuickBooks history), reached only by its address. Posting is turned on from the setup screen (below), which the Organisation page links to. Wherever a bill's posting shows (the bill's tag, banners and history, the bills list, Home, the Inbox and the companion's rail) it names the books it went to: `posting.books` on a bill and a list row, `books` on an Inbox line about the books, and on the bill page `books`, which is where the bill went, else where the team's bills go now. The Accounting page and payments stay QuickBooks only.

## Integration setup (Building)

A harness, in the sense Claude Code is one: a model in a loop picks its next step, with tools, instructions, saved state and limits it cannot override. It sets up an accounting system in a chat with one person: sign in, confirm the company, the study, how you work, a few calls, Go. Admins only, all under `/organizations/:id/integrations/`; the screen is `pages/IntegrationSetup.tsx` at `/organizations/:id/integrations/:system`, reached from the Accounting row on the Organisation page.

The rule: the model decides what to do next; code decides what is allowed and does anything that must be exact.

- **Readers.** `integrations/books.ts` is what any accounting system looks like to it: one shape, read only. `integrations/quickbooks-reader.ts` is QuickBooks in that shape, and `integrations/xero-reader.ts` is Xero in it (below). The harness holds a reader and so holds no way to write: a bill reaches the books only through the posting code above, after its own approval. A failed read is a named `BooksReadError`, never an empty list, and every read is checked against the system's own count and says what is missing. `api/scripts/books-read-check.mts` runs one against a real company on the bench.
- **Connectors and playbooks.** `integrations/connectors.ts` is what the harness needs from a system: is it signed in, a reader, the sign-in request, and the person's yes. `integrations/setup/playbooks.ts` holds the study of each system as instructions. Adding a system should take one of each and change nothing else. Xero took one of each and showed where shared code had QuickBooks in it: a playbook now says whose screen the sign-in is on (`signsInAt`) and its words for what a posted bill leaves out (`leftOutWords`), a connector says whether it `posts`, and the rule every playbook shares says only the person can press Go, leaving what Go does to each playbook's last step. `setConnectorForTests` with `integrations/fixture-reader.ts` runs a whole setup on a company in memory.
- **Xero** (`integrations/xero-reader.ts`, `xero-app.ts`, `xero-connector.ts`, `xero-sign-in.ts`, `xero-fixture.ts`). Decimal reads Xero, and since 12 Nov 2026 posts approved bills to it (above). Until then a Xero setup was a rehearsal: Go recorded the yes and said nothing would post. Those yeses are let go once (`postgres/init/040-xero-rehearsal-yes.sql`), because a yes now turns posting on. A connector that can't post comes in with `posts: false` and its setup is still a rehearsal, and bill coding reads only setups of systems that post (`postingSystems()`). The connection is an `accounting_connections` row under provider `xero`. What is QuickBooks' alone (the Accounting page, its account map, payments) filters provider `quickbooks`, so it never sees that row. Two kinds, by the row's `environment`:
  - `live`, with Decimal's Xero app (`XERO_CLIENT_ID` and `XERO_CLIENT_SECRET` in `api/.env`: a Web app on developer.xero.com whose redirect URIs are `http://localhost:3100/accounting/xero/callback` and `:3200`'s). `GET .../integrations/xero/sign-in` answers with Xero's authorize address and a signed state (`accounting/oauth-state.ts`, shared with QuickBooks; a state says whose sign-in it is, and each callback refuses another's). The scopes are `offline_access`, reading settings and bank transactions, and reading and writing contacts, invoices (bills, linked transactions included) and attachments, which is what posting a bill writes: the granular scopes Xero gives apps made after 2 March 2026. A sign-in from before Decimal posted only reads, so a write refused for its scope says to sign in to Xero again. Xero sends the browser to the public `/accounting/xero/callback`, which exchanges the code, finds the organisation in `GET /connections` by the token's `authentication_event_id`, keeps the tokens and sends the browser back to the setup. A cancel or a failure goes back too, and the conversation says so. The reader reads through `httpXeroClient`: the `xero-tenant-id` header, JSON, a where clause escaped whole, four requests at once per organisation (Xero takes five), a 429's `Retry-After`. A sign-in lasts 30 minutes and its refresh token 60 days unused, replaced each time it is spent. `XeroSession` renews five minutes early or on a 401, reads spending the same refresh token share one renewal, each renewal is stored against the token it spent so a stale read never overwrites a newer sign-in, and a dead refresh token marks the row `needs_reauth`. A 401 for a scope the sign-in never asked for is Decimal's mistake and reads as refused, not as a lost sign-in; a 403 saying the organisation was disconnected on Xero's side reads as a lost sign-in. Disconnecting removes the organisation's connection to the app and revokes the refresh token, best effort. Xero's developer terms forbid scraping its websites, browser automation included, so nothing here drives Xero's screens: a person signs in. They also forbid training on what the API returns. Run on Xero's Demo Company on 2026-11-11: the sign-in, the read (58 categories, 39 vendors, 35 bills and 40 expenses over 24 months, each count and total equal to plain unfiltered pages read by `scripts/xero-read-check.mts`), the questions and Go, then the same read again after the 30-minute sign-in had run out, which renewed it and stored the new pair. Then Disconnect, after which Decimal was gone from the organisation's connected apps in Xero, and a sign-in cancelled on Xero's screen, which came back as `access_denied`. A new Xero login has to add an organisation of its own (a free trial) before Xero offers it the Demo Company.
  - `fixture`, on the bench without the app: a made-up organisation in Xero's own JSON behind a pretend sign-in. `XERO_FIXTURE_FILE`, which production refuses, is set by `scripts/bench.sh` when `synthetic_data/setup-eval/xero/demo.json` exists (made by `generate.mjs`), and `fixtureXeroClient` answers it as Xero's specification describes (pages of 1000 with a count, `where`, `Statuses`, its error statuses and `Retry-After`). With the app configured, a sign-in is real, and rows made this way keep reading the made-up organisation. Nothing posts to it. The setup eval reads the same fixtures in process.

  `/capabilities` says `integrations.xero`, which puts a Xero row on the Organisation page, and `xeroMadeUp`, which gives the setup the made-up organisation's words. In Xero's data a contact has one name (QuickBooks keeps a company name too, so a look-alike group found only through it is lost), bills and spend money have no memo, employees aren't contacts, a location is one more tracking category and reads as a class, and a lapsed organisation is assumed to show `OrganisationStatus` CANCELLED.
- **Saved state** (`integration_setups`, `integrations/setup/record.ts`). Nothing lives in a process between turns. Anything that should get a response (a message, the sign-in coming back, the study finishing) is a waking event on the append-only log, `integration_setup_events`. `harness.ts` takes the turn with an atomic lease, rebuilds everything from the record, runs the model through `runAgent` (`exceptions/agent.ts`), and moves `handled_through_seq` past what it answered. A message sent during a turn waits for the next one. A dead process's lease runs out and `agents/integration-setup.ts` wakes the setup, which only repeats a turn: no tool writes to the books, and answers are keyed by call.
- **The receipt.** The same log, at `GET .../setups/:id/receipt`: each turn's model, playbook version, tokens (with what was read from and written to the cache) and cost at list price (`infra/model-cost.ts`), each tool call with its arguments and the records it brought back, each answer with who gave it and in which message.
- **Limits.** Tokens and turns per setup, three turns in a row without an answer, and the same call failing the same way. At a limit it stops in fixed words, saying where it got to, and the record stays ready to resume. A turn that failed is retried by the sweep rather than at once, so a model that is down for a minute does not use up its tries. While it waits, the view's `retrying` says how many tries failed, of how many, and whether the AI service didn't answer (`service`: an error status, no connection, out of time) or the model didn't manage an answer (`answer`). A stop after failures says which of the two it was.
- **The study and the copy** (`setup/study.ts`, `integrations/copy.ts`, `books_records`). Fixed code reads settings, categories, vendors, and 24 months of bills and expenses into a copy, one company at a time, and works out the findings (`setup/findings.ts`): look-alike vendors, a line coded two ways, a line the team moved to a newer category, what repeats, what a posted bill leaves out, reads that came back short. A moved line isn't a question: both ways saw real use and never overlap, so Decimal learns the newer one and says so, and a person who disagrees can still overrule it. Lines with no words are never coded two ways or moved: Decimal can't fill them in, so an answer about them would change nothing. A look-alike group lists what two or more of its vendors share, comparing an address however its street is written ("Road" or "Rd.", with the country or without) and counting a business's own email domain (not gmail and the like) as shared, though a domain never makes a group by itself. Code also says whether a group reads as one business (`oneBusiness`): each vendor joins the rest by a name or a close spelling with a contact detail in common, or by the same name and nothing that differs, and no account numbers differ. Then the agent recommends making them one; otherwise it says what it sees and asks without leaning, because contact details under different names can be a bookkeeper two businesses share. It never recommends keeping them apart. The model sees each line as it was last written, never the key code compares lines by, with up to three other ways it was written (`alsoWritten`), so one wording never stands for "Electric - Depot 1", "2" and "3" together. The model asks the copy through structured lookups (`look_up`, `summarize`), so it does no arithmetic and never sees minor units. The study runs apart from the chat and tells it by an event. Signing in to another company or disconnecting deletes the copy.
- **Tools** (`setup/tools.ts`). Each checks what it needs itself, so the order holds whatever the model does: reading needs a sign-in, confirming the company or recording an answer needs a person's message on this turn, a call has to cite real records and has a recommendation and a reason. About seven calls at most, two asked at a time, and the rest wait their turn. What takes the same kind of answer is one call, so all the look-alike vendors are one question, and opening another of that kind adds to it. The closing date always is one, and so is who approves when nobody else can: code opens those, and neither can be answered before it has come up in the chat or been answered on its card. The state says whether the person is the primary admin, the only one who can turn No self-approval off. A closing date has to be one the person gave or agreed to, and "never closed" has to be said outright, because a null reads like "don't know". Each tool that reads or saves adds a step to the message in progress (`thoughts`: "Looking through the vendors", "Saving the answer"), so whoever is waiting sees what it is doing.
- **Answers are by name.** The model passes names, as a person says them, and code turns each into a record exactly (the same name, then the same but for case and spacing, then an id) or refuses and says what would work. A later answer changes only what it names. What was saved comes back in words (`inWords`), which is also what the model reads on later turns, so it never handles ids. A value wrapped in its call's name, `{closing_date: {date}}` for `{date}`, is unwrapped (`unwrapped`): Haiku sent the Demo Company's closing date that way.
- **What code writes into a message.** The model writes its sentences; code writes what has to be exact. What was saved on vendors and lines goes above them (`Saved:`), so a person reads what happened rather than what the model made of it. The vendors or lines a question asks about go below them (`list` on `respond`, `listFor`), with their exact names, how much each is used and what they share, and without what they have settled. The model is told not to say what a group shares: Claude Haiku summed four groups up in one sentence that was true of two. Look-alike groups that read as one business come first, so "the first four are one business each" is true of the list. What a posted bill leaves out goes under the message that tells them their books are read (`Worth knowing:`, `leftOutInWords`). A sentence the claims already say comes out of the message (`withoutWhatClaimsSay`), as claims show under it.
- **Send-backs** (`notRightYet` in `harness.ts`, `checkTerminal` on `runAgent`). A message that is too long, asks more than two questions, makes more than five claims or a long one, cites nothing real, puts a list with anything else, skips how they work once their books are read, or leaves them with nothing to do goes back to the model. So does one sent while the person's answer on a question's card failed to save this turn, once, with why: a reply sent in the same breath as the save never saw it fail, and told the person it was saved. After two it stands: the person is waiting. If it still leaves them with nothing to do, code does it: the first question still open, in the words it was opened with and with its list, in a message of its own, or, with none open, Go under the message if Go can be offered.
- **Claims.** A sentence about how the team works carries the refs of the records behind it: something a tool returned this turn, or something in this company's copy. One citing nothing real is dropped, and that goes on the receipt.
- **Go** (`setup/gates.ts`, `goLive` in `setup/service.ts`). `offer_go` only asks: code checks the done conditions and builds the button. It also checks that each look-alike group and two-ways line was named to the person, and that bills already approved in Decimal were told in a claim citing them (`notRaised`). Those bills aren't a question: they never post by themselves, so there is nothing to decide. Anything else can be passed over with a reason, which goes on the receipt and stays passed over; what a question cites can't be, because they have to see what they're asked about. Pressing it checks the conditions again, turns posting on as the person who clicked, and writes `integration_setups.outcome`: closing date, vendor links, line choices, categories in use, what a posted bill leaves out. Posting reads the closing date and vendor links. Bill coding reads the lines, through line memory.
- **The screen** (`pages/IntegrationSetup.tsx`, `setup.css`). The conversation in the bill's chat rows with the reply line pinned under it, and beside them the five steps (sign in, confirm, read, answer, Go), each ticked from the view: `goConditions` by key, the study's steps, how many calls are answered. The questions themselves are in the conversation: while any call is open, the last thing in it is a card on the maroon band a question for you is on in a bill's conversation, one question at a time, with a line to answer it on and arrows through all of them ("2 of 3"), in the order the view lists them, which is the order Decimal asks them. It opens on the first still open. After an answer on it, it stays on that question if Decimal still waits on it, else goes to the next still open. An answered one shows its answer in words and takes a new one. Each question keeps what was typed on it while the person turns through them, and the card steps aside while Decimal takes a reply in. An answer written on a card is a message like any other, sent with the call it answers (`answering` on `POST .../messages`, kept on the message's event), so the questions can be answered in any order: the thread shows the question above the answer, and the model reads a note naming the call before it, that turn and later ones (`cardNote` in `setup/record.ts`), so "31 December 2025" needs nothing around it. The playbook tells the model about the card. Decimal still asks in its own words too, in the thread, and the reply line under the conversation is for anything else. It opens on `GET .../integrations/:system/setups/latest`, finished or not, and looking starts nothing; Start setup is the only thing that does. Buttons come from a message's `actions`, never its words, each on its latest offer only. A sign-in button goes as soon as a sign-in comes back after it: the view's `signIn` gives the latest `signed_in` event and whether the connection is live. It doesn't wait for the company to be confirmed, as `signed_in` among the done conditions does; the screen waited for that until 2026-11-12, so the button stayed while the person read Decimal's question. It comes back if that sign-in stops holding, and stays on one Decimal offers again (the wrong company). The Steps tick Signed in on the same terms. Go shows while `canGo`. Pressing a button greys them all until it is done. Pressing a sign-in leaves the page, so nothing on it clears that, but Back from the sign-in brings the page back as it was left. So `pageshow` clears it, and so does a timer for a trip stopped before it left (`LEFT_MS`, one per sign-in): a sign-in pressed again, then Back, once left Go greyed until a refresh. While Decimal is working (a turn running, `retrying`, the study reading, a person's message unanswered) the page looks again every second and shows what it is doing (`thoughts`, the study's steps, the try it is on); otherwise every five seconds, so another admin's message shows too. Intuit's sign-in lands back on the screen once the organisation has had a setup (`setupScreenFor` in `routes/accounting.ts`), otherwise on Accounting. A finished setup's view says whether its yes still holds (`posting`, from the connector's `postingSince`): `on`; `signed_out`, when Intuit's sign-in ran out, where the screen offers Sign in again (`signInAgain`) because signing in again to the same company picks posting up where it left off; or `off`, after a disconnect or a sign-in to another company, where it offers a new setup (only one setup per system is live at a time, and a finished one doesn't count). Each person's message carries its `author`, since more than one admin can be in a setup.
- **After Go** (`pages/IntegrationPosting.tsx`; `postingView`, `booksClosingDate` and `changeClosingDate` in `setup/service.ts`). While a finished setup's yes holds (`posting` is `on` or `signed_out`), the screen opens on what posting is doing, a settings page whose title sits where the setup's does, and the conversation is a click away, read only, at `?view=conversation`. Connection says which company, who turned posting on and since when (the view's `finished`, from the `go` event), with Sign in again when signed out, the conversation, and Disconnect behind a confirm. What Decimal follows is the closing date in force, then what the setup decided in the API's words (`finished.decisions`, from the outcome, named from the findings or else the copy), how many vendors' lines are coded from history, and what a posted bill leaves out (`leftOutLines`). Only the closing date changes there, because it moves as months close: `PUT .../setups/:setupId/closing-date` (admins; a date not in the future, or `neverClosed`; only on the latest finished setup, because posting reads the one written last and writing an earlier one would put its decisions back in force), logged as `closing_date_changed` with who changed it. Anything else the setup decided takes a new setup. When the books keep a closing date themselves, posting goes by theirs (`closedThrough`), so the screen shows theirs, read only. It is read live in one call, `BooksReader.closingDate()` (Preferences alone, where `company()` takes two), on an endpoint of its own, `GET .../integrations/:system/books-closing-date`, because the books take a second or two to answer and only that row should wait. When they can't be read, the screen shows Decimal's date without saying it is the one in force. Needs attention and Posted come from `GET .../integrations/:system/posting`, the database alone: the bills posting has dealt with since this setup's Go (`postingFrom`; earlier rows belong to an earlier connection), refused or held first, then posted and pending, newest first, fifty of each, every row opening its bill. The bill page and this list read a sync the same way (`postingOf` in `accounting/account-sync.ts`).
- **Evals** (`api/scripts/setup-eval.mts`, fixtures in the gitignored `synthetic_data/setup-eval/`). Eighteen conversations on fixture companies with hidden answers, a model playing the person, code scoring what was saved, a model judging what was said, and a full transcript and receipt for each in `outputs/research/integrations-agent/evals/`. A run prints what it cost at list price, the setup's calls apart from the person's and the judge's, and each scenario's setup cost. A full run takes about 5 minutes. On Claude Haiku 5.5, the default, the setup's calls cost about $0.17 and the person and the judge on Opus about $1.70; on Opus 5.5 the setup's calls cost about $7 (a turn about 6¢, three quarters of it writing the prompt to cache), and on gpt-6-luna about $0.20. With `ANTHROPIC_API_KEY` set, the person and the judge run on Claude Opus 5.5 (`EVAL_PERSON_MODEL` changes it) whatever model the setup runs on, so two agent models compare, but a run is not comparable with one on OpenAI. The judge is noisy, so read what it flags: the code-scored failures are the bar. `SETUP_EVAL_SYSTEM=xero` runs the same eighteen on the same companies as Xero holds them (`synthetic_data/setup-eval/xero/`), through the Xero reader and playbook. There the judge is told Go is a rehearsal, the code scores a location as a tracking category, and the bills approved before connecting need no word, since nothing posts: saying they'd post is the only wrong answer. ## Auth and roles (Live)

`api/src/auth/`. Session tokens, email and password, Google OAuth. `capability-access.ts` maps roles to capabilities and the frontend hides what a user cannot do.

Access has two layers. The tier is `organization_memberships.role`: one primary admin, admins and members. Only the primary admin makes or unmakes an admin or invites one. The job role lives in `approval.person_roles`: a member holds exactly one (bill clerk, approver, payer or viewer; `setRole` replaces it), and an admin holds none. Invitations (`routes/organization-invites.ts`) send no email. Creating one returns its link once, because the token is stored hashed, and the admin sends it themselves. A new invitation to an address replaces any earlier one there that is pending or expired. Revoking works on a pending or an expired invitation, which is how an expired one leaves the list. There is no way yet to remove someone from an organisation or to hand on the primary admin role from the app.

Signing in (`frontend/src/pages/signin/`) is one frame for every way in: Sign in, Create an account, Check your email, joining from an invitation, Create an organisation (`/setup`) and Choose an organisation (`/choose-organization`), the last two outside the app's frame. `landing.ts` decides where someone lands once signed in: an address still to confirm first, then the page they were going to (`?returnTo=`), else their organisation, the one this browser opened last, or the choice. A new account confirms its address with a six-digit code, emailed through Resend. Where nothing is emailed (no Resend settings, or `SEND_EMAIL=false`, which the bench sets and production refuses) the API returns the code as `devEmailVerificationCode` and the page shows it; production never returns it. There is no password reset yet. Creating an organisation refuses a name another one has, whatever the capitals (409 `organization_name_taken`). The public invitation preview carries the job role, and `/capabilities` reports `auth.googleSignIn`, so the Google button shows only where it works.

Your account (`frontend/src/pages/Account.tsx`, at `/profile`) is the same page for everyone. The name changes with `PATCH /auth/me`, which renames the person in the approval engine too (`renamePerson`), so bills and the roster show the new name at once. The password changes with `POST /auth/change-password`: the current one is checked (a 403 `wrong_password`, never a 401, which would sign the person out), the new one needs at least 8 characters, and every other session is deleted while this one stays. The session says `hasPassword`; an account made with Google has none, so there is nothing to change. There is no picture upload: the picture is Google's, or initials. Admins rename the organisation with `PATCH /organizations/:id`, under the rule for creating one: the name must be new whatever the capitals (409 `organization_name_taken`).

Dev sign-in exists only when `DEV_AUTH_SECRET` is set, which it never is in production: `POST /auth/dev/seed`, and the `/dev-login` page, which signs in through the ordinary `/auth/login` and `/auth/register`. Only `@dev.decimal.test` addresses are accepted. Signing up as a seeded person claims the account and keeps the name it was seeded with. `config.ts` refuses this flag and the fake-chain flag in production.

Your account belongs to no organisation, so the frame keeps the one this browser opened last (`rememberedOrganization`). The old global stylesheets (`styles.css`, `styles/canonical.css`, `styles/run-detail.css`, `styles/design-tokens.css`) still load, cut down to the rules the old pages can still match; their bare `.field` rules and focus ring skip anything inside `.ui`, so the kit's own fields and focus show. Read `frontend/src/pages/PAGE-PLAYBOOK.md` before creating or editing any page: the page shapes, the shared classes, the kit and the rules. Colours, shadows and scrims come only from `styles/ui/tokens.css`. **The app reads at 110%.** At the browser's 100% everything was a little small, so `App.tsx` puts `app-zoom` on `<html>` on every page but the landing page, and `html.app-zoom` sets CSS `zoom: 1.1` (`styles/ui/shell.css`). A bill's page undoes it (`.ui.bp` in `bill.css`), as does a dialog or toast shown over it, so a bill reads at the browser's 100% while the sidebar beside it stays at 110%. Under `zoom`, `100vh` and `100vw` are 110% of the window, so anything sized to the window divides by `--app-zoom` (`calc(100vh / var(--app-zoom, 1))`), which is 1 inside a bill's page. A mouse position and `getBoundingClientRect()` are in screen pixels while `offsetWidth`, `scrollTop` and the lengths written to a style are in the element's own, so code that carries a distance from one to the other divides by `zoomOf(el)` from `kit/zoom.ts` (the rules canvas, Home's full screen). Media queries still measure the window, so a breakpoint meant for the zoomed page is its width times 1.1 (sign-in's 836px). The design's artboards are drawn at 100%: to compare a page with them, take `app-zoom` off `<html>`.

The public landing page is `src/pages/landing-v4/`.

## Testing

- `make test` runs the API typecheck, the API tests against `usdc_ops_test`, and the frontend build.
- **Never run `tsx --test` or `npm test` directly inside `api/`.** It inherits the dev database URL and the tests truncate every table.
- `make test-one FILE=tests/x.test.ts [NAME=pattern]` runs one file (or matching tests) against `usdc_ops_test`, for iterating. `make test` still gates every commit.
- `api/tests/companion-safety.test.ts` attacks the companion with a hostile scripted model: every tool with every malformed argument, cross-organisation reads, a (person × action × bill) matrix of card proposals, smuggled requests and junk in answers, double clicks, stale cards, a model that throws or loops. "Changed nothing" is measured by fingerprinting every row of every business table before and after; only the companion's own tables may move. Each protection was deliberately broken once to prove a test catches it.
- `api/scripts/companion-redteam.mts` is the live counterpart, run by hand on the bench against the real model: 38 adversarial cases (direct commands, role abuse, social engineering, instructions hidden in invoice PDFs, invented bills and people, cross-organisation questions, long/foreign/markup input, positive controls), each turn bracketed by a snapshot of the org's business tables. Run from `api/` with `./node_modules/.bin/tsx scripts/companion-redteam.mts [caseId…]` after `make bench`.
- `make bench` starts an isolated stack for agent-driven browser verification. `TESTBENCH.md` is the contract.
- `TESTING-INVOICES.md` specifies the synthetic invoice set. The generator is `scripts/invoice-gen/`.
